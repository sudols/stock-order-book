Three main panels. Left is the order book: a population chart-like structure for bids and asks (both color-coded), top ten each side that is updated continuously. Center part is to place trades for buy or sell with said price and quantity for every order. Right side shows the trade history. Basically shows only the trades that have been matched. Non matched trades are not shown.

Login auth is being done with Firebase's service to avoid spamming and basic bot traffic which it would probably have none, but it is a precaution we took. Layout was kept simple intentionally, since adding too many elements made it look cluttered, plus... it would make the designing harder too, especially on smaller screens. It is mainly a desktop website, so there is no mobile-friendly interface. They will see the desktop version too.

1. WHAT IS THIS PLATFORM

Stock Order Book is a project built by students as an educational simulator made as part of a course named Design Thinking and Innovation course at Bennett University. It shows how a stock order book and matching engine work in a simulated environment. This project exists and is meant only to gain the full 60 marks worth of assessment and lab marks in the said subject in university.

This platform does not connect to any real stock exchange (NSE, BSE, to name a few). It does not place real orders. It does not handle real money. Portfolio balances are virtual numbers with no financial value similar to you. Nothing you do here has any effect on any real market because it's obviously not real, duh.

3. THE DATA YOU SEE

Prices and order flows will either be auto-generated by the market-maker script in the codebase or entered manually during a session and decided as market sees the value. None of it is live or real market data. If a future version adds third-party data, it will only be used once the user is notified.

4. THE DATA WE SEE

Sign-in uses Firebase Authentication. Your email and a Firebase UID are stored to identify your session. So we know who you are and track you down by asking about your Gmail with Google. No financial data, payment or government info is collected, only your email will be stored in a database, along with the hashed password. Order history lives in server memory only and disappears on restart. Not written to any database.

Week 3: Core matching engine work started, and it took longer than expected, because it's the core you silly, obviously it will take time. The first version had a bug where partial fills were not reducing the taker order quantity correctly, so the same order would match against multiple resting orders but still show up in the book as unfilled. Took about two days to find it. Once fixed, unit tests were written for the happy paths and a few edge cases.

Week 4: Added the PortfolioManager and wired it into the matching engine so orders get rejected if the user cannot afford them. Implemented tRPC router with placeOrder and cancelOrder. Firebase token verification was added to middleware. We could finally test placing an order through an HTTP client and see it actually match, this was mostly just running curl command on the endpoints.

Week 5: This was when frontend work started with Zustand and Socket.io client connected and the order book component was a basic table at first, no styling, just proving the data was flowing correctly from server to client in real time. Just enough to test the flow working state.
